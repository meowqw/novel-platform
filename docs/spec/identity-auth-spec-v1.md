# Identity & Authentication — Technical Specification v1.0

**Project:** платформа для авторов ранобэ  
**Status:** Proposed / ready for implementation planning  
**Depends on:** Backend Foundation v1.0 (Laravel 13, PHP 8.4, PostgreSQL 17, Redis 7, Docker Compose, Pest, Pint, PHPStan level 6)  
**Scope:** backend only; no frontend, SEO, social graph, or literary content.

## 1. Цель

Создать первый рабочий бизнес-модуль `Identity` в существующем Laravel-native модульном монолите. Он отвечает за регистрацию, аутентификацию, профиль, верификацию email, восстановление пароля и управление API-токенами. Использовать стандартные возможности Laravel, не вводить полноценный DDD, универсальную RBAC или абстрактные репозитории.

## 2. Ограничения и инварианты

- Один пользователь одновременно может быть автором и читателем. Нет `author`/`reader` ролей и отдельных таблиц.
- Не раскрывать email, пароль, токены, технические флаги и другие приватные поля в публичном профиле.
- Все изменения приватных данных требуют аутентификации; публичное чтение профиля не требует её.
- Не менять бизнес-логику существующего Example-модуля; он остаётся тестовым эталоном, если не согласовано иное.
- Сохранить стандартные компоненты Laravel (auth provider, notifications, password broker, policies, form requests, resources, rate limiting).
- Не создавать пустые директории, интерфейсы, репозитории или сервисы без конкретной потребности.
- Все ответы API JSON, в рамках уже принятого в Foundation формата ошибок/ответов. Не создавать второй конкурирующий формат.
- Все маршруты под `/api/v1`.

## 4. Модель данных

### users

- `id`: UUIDv7, primary key (для нового проекта; если в Foundation уже есть пользователи с другим типом PK, сначала представить план безопасной миграции, не менять тип молча).
- `username`: уникальный, case-insensitive; нормализованная форма, 3–30 символов, латиница, цифры, `_`; резервировать системные имена (`admin`, `api`, `settings`, `login`, `register`, `me` и т.п.).
- `name`: отображаемое имя, 1–80 символов.
- `email`: уникальный, нормализованный, case-insensitive; максимум 254 символа.
- `email_verified_at`: nullable timestamp.
- `password`: хеш, никогда не сериализовать.
- `bio`: nullable text, лимит 1000 символов.
- `avatar_path`: nullable, **только ссылка/ключ на будущий Media-модуль**, загрузка аватаров не входит в v1.
- `created_at`, `updated_at`.

**Case-insensitive уникальность** обеспечить на уровне PostgreSQL (например, уникальный индекс по `lower(username)` и `lower(email)`), не полагаться только на FormRequest. Согласовать с существующей схемой и используемой стратегией нормализации. Не использовать `softDeletes` без отдельного решения.

### personal_access_tokens

Стандартная таблица Sanctum, с учётом UUID пользователя и корректной morph-связи. Не переписывать Sanctum вручную. Для PostgreSQL проверить совместимость миграции и morph key с UUID.

### password_reset_tokens

Стандартный механизм Laravel password broker; не создавать собственные reset-токены.

## 5. Аутентификация

### Базовый режим v1

Sanctum Personal Access Tokens для будущих API-клиентов. Токен выдаётся при логине и регистрации, хранится в базе **только в хешированном виде**, показывается клиенту однократно. Передавать в `Authorization: Bearer <token>` по HTTPS. Не помещать токен в URL или логи.

**Важная оговорка:** для браузерного SPA в дальнейшем предпочтителен штатный cookie-based режим Sanctum, чтобы не хранить bearer-токен в localStorage. В v1 не строить фронтенд, но не закрывать возможность перехода на этот режим.

- Регистрация: email, username, name, password + confirmation.
- Логин: email + password; неверные реквизиты дают одинаковую ошибку без раскрытия существования email.
- Logout: отзыв текущего токена.
- Logout-all: отзыв всех токенов пользователя (включая текущий).
- Токены: список активных токенов без хешей/секретов, отзыв выбранного токена владельцем.
- Для токенов задать разумный срок жизни, например 30 дней; конкретный TTL вынести в config и зафиксировать в документации.
- Верификация email: отправка письма через Laravel Notifications, подписанная ссылка/токен с ограниченным сроком действия; повторная отправка с throttling.
- Сброс пароля: запрос письма и подтверждение нового пароля стандартным password broker; ответ на запрос сброса не должен позволять перечислять аккаунты; после смены пароля отозвать ранее выданные API-токены.
- Изменение email: требуется текущий пароль, новый email становится непроверенным, отправляется новая верификация.
- Изменение пароля: требуется текущий пароль, подтверждение нового, отзыв остальных токенов (политика текущего токена должна быть явно определена и протестирована).

**Email delivery:** локально использовать `log` mailer либо тестовый SMTP sink при его наличии; production SMTP-конфигурация через environment. Никаких реальных SMTP-ключей в репозитории. Для API-сценариев верификации/сброса не предполагать существование frontend-страниц: определить в спецификации безопасный backend-only flow и способ тестирования без UI. Не допускать произвольных redirect URL из запроса.

## 6. API-контракт (проект)

Все маршруты с префиксом `/api/v1`. Названия и семантика фиксируются при реализации в OpenAPI/документации; ниже целевой контракт.

| Метод | Маршрут | Доступ | Назначение |
|---|---|---|---|
| POST | `/auth/register` | guest | Регистрация + токен |
| POST | `/auth/login` | guest | Логин + токен |
| POST | `/auth/logout` | auth | Отозвать текущий токен |
| POST | `/auth/logout-all` | auth | Отозвать все токены |
| GET | `/auth/me` | auth | Текущий пользователь |
| GET | `/auth/tokens` | auth | Метаданные токенов |
| DELETE | `/auth/tokens/{id}` | auth | Отозвать собственный токен |
| POST | `/auth/email/verification-notification` | auth | Повторно отправить верификацию |
| GET | `/auth/email/verify/{id}/{hash}` | signed | Подтвердить email (безопасный backend-only flow) |
| POST | `/auth/password/forgot` | guest | Запрос сброса |
| POST | `/auth/password/reset` | guest + reset token | Сброс пароля |
| PUT | `/auth/password` | auth | Изменить пароль |
| PUT | `/auth/email` | auth | Изменить email |
| GET | `/users/{username}` | public | Публичный профиль |
| PATCH | `/profile` | auth | Обновить собственный профиль |

Текущий пользователь может быть доступен через `/auth/me`, без дублирования `/profile` GET. Рекомендуемый ответ ресурса: `id`, `username`, `name`, `bio`, `avatar_url` (nullable), `created_at`; приватный ресурс дополнительно содержит `email`, `email_verified_at`. Никогда не отдавать `password`, `remember_token`, хеши токенов и внутренние поля.

### HTTP-коды

- 200 — чтение/изменение, 201 — регистрация, 204 — успешный logout/revoke.
- 401 — неаутентифицированный запрос; 403 — недостаточно прав.
- 404 — несуществующий публичный профиль или чужой токен (не раскрывать его существование).
- 422 — ошибки валидации; 429 — превышение лимитов.
- Ошибки API должны быть согласованы с Foundation; не внедрять произвольную envelope-структуру.

## 7. Валидация и безопасность

- Password: минимум 12 символов, подтверждение, хеширование штатным Laravel Hasher. Не навязывать произвольные сложные правила без продуктовой причины.
- Rate limits отдельно для регистрации, логина, forgot/reset password, resend verification. Для логина учитывать IP и нормализованный идентификатор; не использовать IP как единственный ключ.
- Case-insensitive уникальность `email`/`username` на уровне БД; корректно обрабатывать race condition при параллельной регистрации.
- Запретить mass assignment произвольных полей (особенно `email_verified_at`, `id`, служебные атрибуты).
- Профиль редактирует только владелец. В v1 не нужен административный API и RBAC.
- Секреты и токены не должны попадать в logs, exceptions, dumps или responses (кроме однократной выдачи plaintext bearer token).
- CORS, trusted proxies, HTTPS, APP_DEBUG=false и cookie security в production конфигурируются согласно Foundation; не открывать CORS на `*` с credentials.
- Для email verification использовать штатные подписи/срок действия и защиту от повторных запросов.
- При удалении/отзыве токена проверять владение на уровне запроса к БД.

## 8. Интеграция с модулями

`Identity` — владелец учётной записи. Другие модули могут ссылаться на `user_id`, но не должны менять пароль, email или данные аутентификации напрямую. На текущем этапе допустима стандартная Eloquent-связь с `User`, без искусственного `UserRepository` и дополнительных interfaces. Публичный профиль — ресурс Identity. Отдельные права на произведения и публикации появятся в их собственных модулях.

## 9. Инфраструктура

- Использовать существующие `nginx`, `app`, `worker`, `postgres`, `redis`; новых обязательных сервисов не добавлять.
- Mail transport configurable через `.env`, для локальных проверок допустим `MAIL_MAILER=log`.
- Очереди для отправки писем при необходимости используют текущий worker; при Redis без persistence документировать риск потери ожидающих задач при перезапуске. Для критичных писем допустима синхронная отправка на раннем этапе либо database queue после отдельного решения.
- Миграции должны выполняться через существующий `make migrate` и работать на чистой БД.
- Никаких изменений production Docker без необходимости.

## 10. Тесты и качество

Обязательные Pest Feature/Unit тесты:

1. Успешная регистрация; повторная регистрация с тем же email/username в другом регистре запрещена.
2. Ошибки валидации, запрещённые username, слабый пароль.
3. Успешный логин; неверные credentials; rate limit.
4. `auth/me` для авторизованного и гостя; отсутствие приватных полей в публичном ресурсе.
5. Logout отзывает текущий токен; logout-all отзывает все; нельзя отзывать чужой токен.
6. Обновление собственного профиля; запрет изменения служебных полей.
7. Отправка/повторная отправка верификации, подтверждение, просроченная/невалидная подпись.
8. Запрос сброса пароля без user enumeration; корректный/некорректный/просроченный reset token; отзыв токенов после reset.
9. Смена email сбрасывает статус верификации; смена пароля требует старый пароль.
10. Все миграции проходят на чистой PostgreSQL; Example и health endpoints не регрессируют.

Использовать `Notification::fake()`/`Mail::fake()` где уместно, реальные проверки через PostgreSQL в CI. `make quality`: Pest + Pint + PHPStan level 6 без регрессий. При необходимости обновить CI так, чтобы тесты Identity запускались на PostgreSQL, а не только на SQLite.

## 12. План реализации для Cursor

**Сначала без кода:**

1. Изучить реальную структуру текущего репозитория, migrations, User, auth config, `AGENTS.md`, rules, тесты и API conventions.
2. Проверить Laravel 13 / Sanctum / PHP 8.4 совместимость с текущими зависимостями.
3. Сравнить существующую модель пользователей с целевой и предложить миграции, включая UUIDv7 и уникальность без учёта регистра.
4. Выбрать канонический класс `User` и описать владение им со стороны Identity.
5. Уточнить способ backend-only email verification/password reset, сроки жизни токенов и правила logout.
6. Составить разбитый на небольшие PR/итерации план и критерии проверки каждой.
7. Запросить согласование перед изменением кода.

**Рекомендуемые итерации после согласования:**

- I. Схема пользователей + миграции + тесты БД.
- II. Регистрация, логин, Sanctum, `me`, logout + тесты.
- III. Публичный/приватный профиль + тесты.
- IV. Верификация email, reset/change password + тесты.
- V. Token management, throttling, API docs, quality gate.

## 13. Definition of Done

- Все запланированные endpoints работают и документированы.
- `make up`, `make migrate`, `make health`, `make quality` работают на чистом окружении.
- Миграции и тесты выполняются на PostgreSQL, не затрагивая локальные пользовательские данные.
- CI зелёный, production image по-прежнему собирается.
- Нет новых обязательных контейнеров, ненужных абстракций и скрытых кросс-модульных зависимостей.
- Приватные поля не раскрываются, токены корректно отзываются, критичные операции защищены rate limiting.
- README, архитектурная документация и current-state отражают фактическое состояние кода.

## 14. Не входит в v1

- Frontend и мобильное приложение.
- OAuth/social login, 2FA, passkeys.
- Платные роли, сложная RBAC/ACL и административная панель.
- Подписки, произведения, комментарии, уведомления о главах.
- Реальная загрузка аватаров, Media-модуль.
- Удаление аккаунта и экспорт пользовательских данных (спроектировать отдельно перед публичным запуском).
- AI-функции и аналитика.

## 15. Инструкция агенту

Реализуй Identity только после изучения существующего проекта и согласования плана. Не меняй структуру Laravel ради формального следования архитектурным шаблонам. Используй встроенные механизмы Laravel и существующие соглашения Foundation. При несовпадении этой спецификации с фактическим состоянием репозитория сообщи о конфликте и предложи минимальное решение, не принимай молча разрушительных решений.
